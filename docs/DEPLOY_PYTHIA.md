# Deploying mnemos-api on PYTHIA

The real procedure for the production MNEMOS instance on PYTHIA
(the fleet orchestration host). It replaces `deploy/mnemos-deploy-latest.sh` and
`/etc/mnemos/docker-compose.mnemos-api.yml`, which describe the Docker
Compose layout PYTHIA left in July 2026. Do not use them.

Facts below were read from the live host on 2026-11-03 (read-only).

## What runs where

| Piece | How it runs | Notes |
|---|---|---|
| `mnemos-api` (REST :5002 + MCP-HTTP :5004) | **rootful podman** container, systemd unit `mnemos-api.service`, generated by the quadlet `/etc/containers/systemd/mnemos-api.container` | `Exec=/usr/local/bin/mnemos-serve-api-and-mcp` starts `mnemos serve` then `mnemos serve mcp-http` once `/health` answers; either dying exits the container and `Restart=always` brings both back |
| Oracle (the corpus) | **Docker** container `pythia-oracle` on :1521 | Docker is a separate engine on PYTHIA (also runs nats, grafana, prometheus, cadvisor, the fleet registry). `docker` cannot see podman containers and vice versa |
| Embeddings | `mnemos-embed-bge-m3.service` (llama.cpp, :8092) | |
| Cache | `redis-mnemos.service` (:6379) | `redis-server.service` is masked |
| TLS fronts | `mnemos-mcp-tls.service` (socat :5444 -> :5004), `graeae-dash-tls.service` (:5443 -> :5005) | |
| Hive bus | `graeae-hive.service` (:5005) | separate repo; not part of this roll |

Quadlet essentials: `Network=host`; env files `/etc/mnemos-http-mcp.env`,
`/etc/mnemos/api-keys.env`, `/etc/mnemos/mnemos-api.env` (DSN, backend,
ports); volumes `mnemos-api-data:/data` (pantheon catalog, local SQLite
side stores, older backups; about 550 MB), `/etc/mnemos/config.toml` (ro),
`/etc/mnemos/api_keys.json`, `/etc/mnemos/rclone.conf` (ro),
`/etc/mnemos/codex-oauth/auth.json`, `/home/jasonperlow/models` (ro);
`HealthCmd=curl -fsS http://localhost:5002/health`.

Inside the image Python imports `/app/mnemos` first and
`/usr/local/lib/python3.13/site-packages/mnemos` second (`mnemos` is a
namespace package spread over both). An overlay that copies a file into the
wrong one of the two trees is silently inert; check with
`podman exec mnemos-api python3 -c 'import <module> as m; print(m.__file__)'`.

## How images are built

Published chain (repo root): `Dockerfile.core` -> `Dockerfile.everything`
-> `Dockerfile.enterprise`, released as `ghcr.io/ncz-os/mnemos-enterprise:<version>`
(see `docs/INSTALL.md`, `docs/OPERATIONS.md`).

PYTHIA then adds local overlay layers on top, one per hot fix, tagged
`localhost/mnemos-enterprise:<version>-<topic>-<YYYYMMDD>`. The running
image `7.0.5-pantheon-catalog-20261025` is:

```
ghcr.io/ncz-os/mnemos-enterprise:7.0.5          core c2dd6bfa, built 2026-09-27
 + 7.0.5-hive-20261017                          mnemos.git feat/mcp-hive-tools-20261017 (mcp/stdio.py, mcp/tools/hive.py)
 + 7.0.5-pantheon-codex-fix-20261018            pantheon router.py
 + 7.0.5-pantheon-catalog-20261025              pantheon.git main eef8cd1 (catalog.py, router.py)
```

The last overlay's context is `~/Projects/pantheon-deploy-20261025/overlay/`
on PYTHIA:

```
FROM localhost/mnemos-enterprise:7.0.5-pantheon-codex-fix-20261018
USER root
COPY catalog.py /usr/local/lib/python3.13/site-packages/mnemos/domain/pantheon/catalog.py
COPY router.py  /usr/local/lib/python3.13/site-packages/mnemos/domain/pantheon/router.py
USER mnemos
LABEL org.mnemos.overlay="pantheon-codex-catalog" org.mnemos.overlay.source="pantheon.git main eef8cd1"
```

Rules for a new tag:

- Build as root (`sudo podman build -t localhost/mnemos-enterprise:<tag> <dir>`),
  because the service uses root's image store.
- Overlay only whole files from a named commit, and record the source in
  `org.mnemos.overlay.source`. Never copy a file from a branch whose other
  modules the image does not have.
- Prefer a full rebuild from the published chain once overlays stack more
  than two deep; overlays hide which core commit actually runs.
- Keep the previous tag in local storage until the new one has run a full
  day; it is the rollback target.

## Rolling a new tag

Use `scripts/deploy_pythia.sh`. It is dry-run by default.

1. **Announce.** Post the window on Hive topic `orchestrator.coordination`
   (the lane holding PYTHIA root does the restart; other lanes hold MNEMOS
   writes and MCP sessions until the all-clear). The restart drops every
   MCP session and in-flight GRAEAE consult.
2. **Dry run** and read every line:
   `sudo scripts/deploy_pythia.sh --image localhost/mnemos-enterprise:<tag>`
3. **Apply:**
   `sudo scripts/deploy_pythia.sh --image localhost/mnemos-enterprise:<tag> --announced --apply`

What the script does:

| Step | Command | Fails with |
|---|---|---|
| preflight | quadlet present; both new and previous image in local storage; current `/health` OK | exit 1, nothing changed |
| backup 1 | `podman volume export mnemos-api-data --output /var/lib/mnemos-deploy/<stamp>/mnemos-api-data.tar` | exit 2 |
| backup 2 | STYX one-shot from the **new** image against the still-running old API: `podman run --rm --network host --env-file /etc/mnemos/styx-r2.env <new> python3 -m mnemos.tools.styx backup` (this is the Oracle corpus, vault included, encrypted to R2) | exit 2 unless `--skip-styx "<reason>"` |
| roll | rewrite `Image=` in the quadlet, `systemctl daemon-reload`, `systemctl restart mnemos-api.service` | |
| health | poll `http://127.0.0.1:5002/health` (default 180 s) | |
| rollback | on timeout: save `podman logs --tail 80` to the backup dir, restore the previous `Image=`, reload, restart, poll again | exit 3 (rolled back) or exit 4 (rollback also unhealthy: page a human; volume tar is in the backup dir) |

`/var/lib/mnemos-deploy/history.log` records every roll and rollback.

The volume export does not contain the corpus (Oracle lives in the Docker
container); STYX does. Oracle-level backup of `pythia-oracle` is out of this
script's scope.

## Migrations

The Oracle backend runs `ensure_schema()` on first connect: idempotent,
forward-only DDL from `mnemos/db_migrations/migrations_oracle/`. A new tag
therefore migrates on its first start. Consequences:

- Read the new tag's migration list against the running one before rolling
  (`ls mnemos/db_migrations/migrations_oracle/` at both commits).
- Rollback after a migration runs the old code on the newer schema. The
  migrations are additive, so this normally works; a migration that drops or
  renames anything needs a written restore plan (STYX artifact from step 2)
  before the roll.

## Keys and config

Provider registries load once at import. After changing
`/etc/mnemos/api_keys.json`, `/etc/mnemos/api-keys.env`,
`/etc/mnemos/mnemos-api.env` or `/etc/mnemos/config.toml`, restart
`mnemos-api.service` (announced, as above). Every enabled
`[graeae.providers.*]` block needs `price_in` and `price_out`, otherwise
budgeted calls fail with `CostReservationConflict: provider pricing
unavailable for budgeted attempt`. On 2026-11-03 six enabled blocks lacked
both: `arcee-trinity-large`, `claude`, `openai`, `xai`, `fireworks`, `groq`.

## Verification after a roll

```
curl -fsS http://127.0.0.1:5002/health
podman inspect mnemos-api --format '{{.ImageName}} {{.State.Health.Status}}'
journalctl -u mnemos-api --since -10min --no-pager | grep -E 'ERROR|Traceback' | head
```

Then, from any MCP client: a MNEMOS search that should hit a known memory,
and one small GRAEAE consult (check `finish_reason`, not only the score).
Finally run the backup for real: `sudo systemctl start mnemos-styx-r2.service`.

|---|---|---|

### Model registry sync

`deploy/pythia/mnemos-model-sync.service` is the only model-sync unit. It
runs `scripts/sync_provider_models.py` inside the container as root
(`podman exec`): the live unit's `docker exec mnemos-api` drop-in has
failed every day (`No such container: mnemos-api`) because the container is
podman, not Docker; registry sync log's newest row is 2026-10-01 21:31Z.

`graeae-model-sync.service` is retired: it ran the same script from the
host venv as `jasonperlow` (so it could not read root-owned 0640
`/etc/mnemos/config.toml`, and should not: that file holds provider keys),
carried a plaintext DSN in the unit, and its second step
(`scripts/update_graeae_config.py`) needs a Postgres model registry.

Install (as root):

```
install -m 0644 deploy/pythia/mnemos-model-sync.service deploy/pythia/mnemos-model-sync.timer /etc/systemd/system/
rm /etc/systemd/system/mnemos-model-sync.service.d/10-docker-fix.conf
install -m 0600 deploy/pythia/model-sync.env.example /etc/mnemos/model-sync.env   # then set MNEMOS_RELOAD_TOKEN
systemctl disable --now graeae-model-sync.timer
systemctl daemon-reload
systemctl start mnemos-model-sync.service; journalctl -u mnemos-model-sync -n 30 --no-pager
```

The old drop-in and unit carry the reload-providers bearer token in
plaintext; once `/etc/mnemos/model-sync.env` holds it, the old files are
gone, and the token should be rotated.

## STYX recovery when nightly backups fail

Check what reached the destinations (read-only):

```
set -a; . /etc/mnemos/styx-r2.env; set +a
podman exec -e MNEMOS_STYX_DESTINATION -e MNEMOS_STYX_R2_ACCOUNT_ID -e MNEMOS_STYX_R2_BUCKET \
  -e MNEMOS_STYX_R2_ACCESS_KEY_ID -e MNEMOS_STYX_R2_SECRET_ACCESS_KEY -e MNEMOS_STYX_HOST_LABEL \
  -e MNEMOS_STYX_AGE_RECIPIENT -e MNEMOS_STYX_SOURCE_MODE -e MNEMOS_STYX_HTTP_ENDPOINT \
  -e MNEMOS_STYX_HTTP_TOKEN -e MNEMOS_STYX_MIN_RECORDS mnemos-api python3 -m mnemos.tools.styx verify
```

The 2026-11-01..03 failures (`materialized MPF record count does not match
validated stream (28415 != 28418)`) came from keyset-seam duplicates in the
deployed server plus two client counters that counted different sets; fixed
on branch `opus/mnemos-pythia-ops-20261103`. Until a tag with that fix is
rolled, take a backup with the fixed client files bind-mounted into a
one-shot container of the current image (the running service is untouched):

```
SRC=/path/to/mnemos-checkout-at-the-fix      # root-readable
IMG=$(podman inspect mnemos-api --format '{{.ImageName}}')
for env in styx-r2 styx-rclone; do
  podman run --rm --network host --env-file /etc/mnemos/$env.env \
    -v /etc/mnemos/rclone.conf:/home/mnemos/.config/rclone/rclone.conf:ro \
    -v $SRC/mnemos/tools/export_stream.py:/app/mnemos/tools/export_stream.py:ro \
    -v $SRC/mnemos/tools/styx/source.py:/app/mnemos/tools/styx/source.py:ro \
    "$IMG" python3 -m mnemos.tools.styx backup
done
```

Each run prints a JSON receipt; `"ok": true` and an artifact name per
destination is success. Re-run `styx verify` afterwards.
