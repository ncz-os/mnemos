# MNEMOS v6.2 — Nexus pattern adoption (design draft)

**Scope:** three patterns adopted from `bubblefish-tech/nexus` audit (2026-05-23, MNEMOS memory `nexus-audit-prs-2026-05-23`). Land after v6.1 ships.

**Source PRs upstream:** [nexus #9](https://github.com/bubblefish-tech/nexus/pull/9), [#10](https://github.com/bubblefish-tech/nexus/pull/10), [#11](https://github.com/bubblefish-tech/nexus/pull/11) (correctness + perf — not the features adopted here, but evidence the source codebase was read at depth).

**Why these three together:** all three change `memories` read/write semantics. Audit chain rides the write path; retrieval profiles + per-category decay ride the search path. Co-shipping lets us do one migration + one bench + one blog post.

---

## 1. Ed25519 + Merkle audit chain (replaces last-write-wins)

### Problem

Today every memory write is unconditional UPSERT. `mnemos/persistence/*/repos.py::MemoryRepository.upsert` overwrites prior content with no tamper-evidence. Federation peers cannot prove their replica matches the primary's history — only the current row. A compromised primary (or replayed feed payload) is indistinguishable from a legitimate edit.

Audit-trail policy in `consultations.py` returns 503 when audit storage is missing, which proves the gate exists for one route. Memory writes have no equivalent.

### Design

Append-only `memory_audit_chain` table per backend. Each memory write emits one chain entry **before** the row UPSERT commits. Chain entries link by SHA-256 of the prior entry — Merkle-linear over per-memory history, Merkle-tree across the global write log on a 1-minute cadence (matches federation feed window).

#### Per-entry shape

```
memory_audit_chain (
  entry_id          RAW(16)   PK     -- UUIDv7
  memory_id         RAW(16)          -- target memory
  prev_entry_id     RAW(16) NULL     -- NULL for first write of memory_id
  prev_entry_hash   RAW(32) NULL     -- SHA-256 of prev row's canonical bytes
  op                VARCHAR2(16)     -- 'create' | 'update' | 'delete' | 'archive'
  payload_hash      RAW(32)          -- SHA-256 of canonical content+metadata
  writer_id         VARCHAR2(128)    -- caller user_id or 'fed:pythia'
  writer_pubkey     RAW(32)          -- Ed25519 public key
  signature         RAW(64)          -- Ed25519(canonical_entry_bytes)
  signed_at         TIMESTAMP WITH TIME ZONE
  global_root       RAW(32) NULL     -- Merkle root of 1-min window once sealed
  global_seq        NUMBER NULL      -- monotone position within sealed window
)
PRIMARY KEY (entry_id)
INDEX memory_audit_by_memory (memory_id, signed_at)
INDEX memory_audit_by_root (global_root)
INDEX memory_audit_unsigned (signed_at) WHERE global_root IS NULL
```

Canonical bytes for `payload_hash` = JCS (RFC 8785 §3.2.3 UTF-16 sort, **nexus PR #9 fix applied**) over `{id, content, category, subcategory, metadata, embedding_hash}`. Embedding goes in as a SHA-256 of its float32 bytes, not the bytes themselves, so reshipping an embedding for `copy_embeddings` (v6.1 F-1) doesn't change the audit hash.

Canonical entry bytes for `signature` = JCS over every column except `signature` itself and `global_root`/`global_seq` (those are populated post-sign by the sealer).

#### Per-memory verification

Walking `prev_entry_hash` from the newest entry back to NULL reconstructs the full history of one memory and proves no tampering with intermediate states. Equivalent to `git log --follow` for one row, but cryptographically verifiable.

#### Global Merkle root

Background worker `mnemos/workers/audit_sealer.py` runs once per 60s:

1. `SELECT entry_id, signature, signed_at FROM memory_audit_chain WHERE global_root IS NULL ORDER BY signed_at` — claim the unsealed window with `FOR UPDATE SKIP LOCKED`.
2. Sort entries by `signed_at, entry_id` (stable).
3. Compute Merkle root using SHA-256 over `(entry_id || signature)` leaf-by-leaf, pad-with-zero to power of two.
4. `UPDATE` the window setting `global_root` + `global_seq`.
5. Publish `(window_start, window_end, root)` to a new `memory_audit_roots` table (timestamp + root + entry_count + signed_by_root_key).
6. Sign the root with a per-instance Ed25519 root key (long-lived, KMS-stored).

Replicas / auditors fetch `memory_audit_roots` via `/v1/federation/audit_roots`. Given a root + a memory_id, they can request the Merkle inclusion proof for that memory's window-local entries via `/v1/audit/proof?entry_id=X&root=Y`.

#### Federation interaction

Federation feed (`/v1/federation/feed`) becomes audit-aware:

- Each replicated memory row carries `latest_entry_id` + `latest_entry_hash`.
- Replica verifies that its own `prev_entry_hash` for that memory matches what the primary claims its prior was. Mismatch → reject the feed payload, log, halt the peer.
- Replica writes its own audit entries for the inbound write (op=`replicate`), chaining to the primary's `latest_entry_id` via `prev_entry_id`. The audit chain becomes a federated Merkle DAG, not a per-host linear chain.

This catches: replay attacks (prev_entry_hash mismatch), split-brain after partition (divergent global roots for same window), compromised peer pushing fabricated rows (Ed25519 signature mismatch).

#### Key management

| Key | Lifetime | Storage | Purpose |
|---|---|---|---|
| Per-writer Ed25519 | session | derive from `MNEMOS_SESSION_SECRET` + user_id via HKDF-SHA256 | sign individual audit entries |
| Per-instance root Ed25519 | instance lifetime | env `MNEMOS_AUDIT_ROOT_PRIVKEY` (base64), public in `/v1/audit/pubkey` | sign global roots |
| Per-peer Ed25519 | peer lifetime | `federation_peers.audit_pubkey` column | verify inbound root signatures from peer |

`MNEMOS_AUDIT_ROOT_PRIVKEY` mandatory at startup when `MNEMOS_AUDIT_CHAIN=on` (default in v6.2). Same fail-loud pattern as v6.1 P3 #38 (session-secret hardening).

#### Constant-time auth compare (defensive carry-over from nexus audit)

Bearer-token compare in `mnemos/api/main.py` currently uses `==`. Switch to `hmac.compare_digest`. Trivial change, defense against per-byte timing leak. Same pattern as nexus uses with `subtle.ConstantTimeCompare`. Ship in the v6.2 PR even though it's orthogonal — keeps the auth surface tidy under the same review.

#### Backend mapping

| Operation | PG | Oracle | Db2 |
|---|---|---|---|
| Insert entry + UPSERT memory atomically | `BEGIN; INSERT...; UPSERT...; COMMIT` (default isolation) | same, `SERIALIZABLE` | same, `RR` (Repeatable Read) |
| Claim unsealed window | `SELECT ... FOR UPDATE SKIP LOCKED` | `SELECT ... FOR UPDATE SKIP LOCKED` (since 11g) | `SELECT ... USE AND KEEP UPDATE LOCKS SKIP LOCKED DATA` (Db2 11.5+) |
| Merkle root index | regular b-tree | regular b-tree | regular b-tree |

SQLite: same shape, single-writer is fine (already noted as dev-only per v6.1 P3 #43).

### Acceptance

- Writing a memory inserts one chain entry before commit; rollback wipes both
- `mnemosctl audit verify <memory_id>` walks the chain end-to-end, reports OK / break-at-entry / signature-mismatch
- `mnemosctl audit verify-window <root>` reconstructs Merkle and compares
- Federation pull rejects payload with `prev_entry_hash` mismatch and logs the offending peer URN
- 10-second pull-the-plug test: kill the API mid-write, restart, verify chain still consistent (no half-written entry)
- Adversarial test: replay a stale federation payload, expect HTTP 409 + audit log entry
- Bench: ≤ 8% p99 write-latency overhead vs v6.1 baseline at 50 writes/sec sustained on Oracle backend (DG primary)

## 2. Retrieval profiles on `/v1/memories/search`

### Problem

Current `/memories/search` has a single behavior: semantic search → cache → re-rank by recency. Different consumers want different tradeoffs:

- An agentic skill calling `portfolio_ask` wants the cheapest answer that's likely-right — 50ms p99, 20 hits, semantic only
- A `synthesize` command sweeping 12 sections wants deep recall — 5s p99 budget, 200 hits, semantic + FTS + cross-encoder rerank
- A user typing in mnemos-desktop wants interactive feel — 200ms p99, 50 hits, mixed strategy

Today they all share one pipeline + one cache. Adding `?profile=` is cheap; the alternative is per-consumer flags that drift apart over time.

### Design

Add `profile` field on `MemorySearchRequest` with three values:

| Profile | Pipeline | Limit cap | Cache TTL | Rerank | Notes |
|---|---|---|---|---|---|
| `fast` | semantic-only, no rerank | 25 | 5 min | none | default for agent skills; targets <100ms p99 |
| `balanced` | semantic + FTS union, recency-weighted score | 100 | 5 min | none | default for interactive callers; matches today's behavior |
| `deep` | semantic + FTS + KG-edge expansion, cross-encoder rerank top-100 → 30 | 200 | 30s (less cacheable) | BAAI/bge-reranker-v2-m3 on CERBERUS | for `synthesize` / `narrate` |

When `profile` is omitted: server picks `fast` if caller has agent-style API key scope (new from v6.1 P1 #39), `balanced` otherwise. Backward-compatible — existing callers see no change.

#### Implementation surface

```
mnemos/domain/search/
  __init__.py
  profile.py              # SearchProfile enum + pipeline registry
  pipeline_fast.py        # semantic-only, no rerank
  pipeline_balanced.py    # current behavior, factored out of memories.py
  pipeline_deep.py        # adds FTS union + KG expand + cross-encoder
  reranker.py             # CERBERUS HTTP client for bge-reranker-v2-m3
```

`memories.py::search_memories` becomes ~30 lines: parse → resolve profile → dispatch → cache.

#### Cross-encoder rerank for `deep`

Runs against CERBERUS llama.cpp on port 8080 OR a small dedicated rerank server. Cross-encoder needs sequence pairs; budget = 100 pairs × ~500 tokens each = 50K tokens per `deep` call. At gemma-4-31B speeds (~17 tok/s for the RiskyEats narrative model), unworkable. Use a small bi-encoder rerank server with `BAAI/bge-reranker-v2-m3` (smaller, faster, rerank-specific) — needs separate deployment on CERBERUS:

```
# /etc/systemd/system/mnemos-reranker.service
ExecStart=/opt/text-embeddings-inference/text-embeddings-router \
  --model-id BAAI/bge-reranker-v2-m3 \
  --port 8090 \
  --max-batch-tokens 16384
```

Hosted alongside existing `:8080` gemma + `:11434` Ollama. ~2GB VRAM (the 4500 ADA has 24GB; fits comfortably).

#### Caching invariant

Cache key incorporates `profile`. Per-profile TTL. `_invalidate_search_cache_on_write` (memories.py:175) scans `mnemos:search:*` which already covers all profiles.

#### Telemetry

Add to `/v1/admin/search_stats`:

```
{
  "profile": "fast",
  "calls_5m": 1421,
  "p50_ms": 38,
  "p99_ms": 92,
  "cache_hit_rate": 0.61
}
```

Lets us prove profile budgets are met before promoting `fast` to default for agent scope.

### Acceptance

- `profile=fast|balanced|deep` accepted on `/memories/search`; unknown values → 400
- `balanced` produces identical results to current implementation (golden test)
- `fast` p99 ≤ 100ms at 10 QPS sustained on Oracle backend with 100K memories
- `deep` p99 ≤ 5000ms with cross-encoder rerank populated from CERBERUS
- Telemetry exports per-profile latency histograms via existing Prom endpoint
- Backward compat: no `profile` param → server resolves per scope, no behavioral change for current callers

## 3. Per-category exponential temporal decay

### Problem

`recency_weight` on `/memories/search` is global. A `feedback` memory ("user wants terse responses") stays useful for years; a `project` memory ("merge freeze begins 2026-03-05") is stale a week later. Single decay constant treats both the same — boosts the stale project memory or buries the durable feedback memory.

Same problem on the rerank side: `boost_recency=true` applies one half-life everywhere.

### Design

Per-category half-life table, evaluated at search time, applied multiplicatively to base score.

#### Table

```
memory_category_decay (
  category        VARCHAR2(64) PK
  half_life_days  NUMBER  NOT NULL
  decay_kind      VARCHAR2(16) NOT NULL  -- 'exponential' | 'sigmoid' | 'none'
  floor           NUMBER  DEFAULT 0.0    -- minimum multiplier (0 to 1)
)
```

Seeded with:

| Category | half_life_days | decay_kind | floor | Rationale |
|---|---|---|---|---|
| `feedback` | 365 | exponential | 0.5 | user preferences slowly evolve; never fully forget |
| `rules` | 730 | exponential | 0.7 | even older rules are usually still applicable |
| `user` | 365 | exponential | 0.6 | who-the-user-is shifts slowly |
| `reference` | 180 | exponential | 0.3 | external systems get re-pointed; old endpoint refs stale fast |
| `project` | 60 | exponential | 0.05 | merge dates / sprint notes go stale within a quarter |
| `facts` | 90 | exponential | 0.2 | factual claims drift; verify before relying |
| `infrastructure` | 30 | exponential | 0.1 | fleet topology changes, host roles rotate |
| `credentials` | 14 | sigmoid | 0.0 | rotated keys are toxic — drop fast |
| `working` | 7 | exponential | 0.0 | session scratch; should decay rapidly |
| `(default)` | 180 | exponential | 0.1 | unknown category fallback |

`sigmoid` for credentials means the score collapses fast around the half-life threshold rather than smoothly tapering — old keys are not "less useful," they're "actively wrong."

#### Score formula

For a hit `m` with category `c` and age `t` (days):

```
base_score   = semantic_similarity OR (semantic + fts_blend)
recency_mult = max(floor[c], exp(-ln(2) * t / half_life_days[c]))
final_score  = base_score * recency_mult
```

`sigmoid` kind uses `1 / (1 + exp(k*(t - half_life_days)))` with k chosen to give 95% drop within ±half_life × 0.3.

#### Per-request override

`MemorySearchRequest.decay_overrides: Dict[str, float] | None` lets callers patch the table for a single search. Useful for `synthesize` which may want to ignore decay entirely:

```python
request.decay_overrides = {"*": 1.0}  # disable decay across all categories
```

#### Admin endpoint

```
GET  /v1/admin/category_decay         -- list current table
PUT  /v1/admin/category_decay/{cat}   -- update half_life/kind/floor (root only)
POST /v1/admin/category_decay/reseed  -- reset to defaults
```

Same auth posture as `/v1/admin/sessions` today.

#### Backend mapping

The category-decay multiplier evaluates in Python after the SQL recall, not inside the DB. Three reasons:
1. The table is tiny (≤20 rows). Pulled into a process-local TTL cache on first read, refreshed every 60s.
2. The decay math is post-recall reranking, not a recall filter. Filtering by score in SQL would either (a) prune real hits before rerank or (b) require executing `exp()` in SQL per row per backend, which is fine on PG/Oracle/Db2 but flat-out broken on SQLite.
3. Keeps the SQL identical across backends. Saves four-way porting work.

### Acceptance

- Seed migration ships table + 9 default rows
- Search ranking changes match a golden dataset (10 prepared memories per category, expected ordering at t=0/30/180/365 days)
- `recency_weight` query param still works (becomes a multiplier on the per-category decay — "scale all half-lives by this")
- Admin endpoints accept root-only edits + reseed
- Telemetry: `/v1/admin/search_stats` reports per-category decay multipliers applied per search profile
- Documentation: new entry in `MEMORY_ARCHITECTURE.md` explaining the table

## Cross-cutting

### Migration sequencing

Order matters — audit chain first because retrieval profiles + decay change scoring outputs, and we want a clean audit-trail anchor before behavior changes ride on top:

1. **M-2.2.1** Audit chain table + sealer worker (no behavior change — existing reads still work, writes are decorated)
2. **M-2.2.2** Constant-time auth compare (1-line patch, no migration)
3. **M-2.2.3** Reranker service on CERBERUS + retrieval profile dispatcher (additive; balanced=current)
4. **M-2.2.4** Per-category decay table + score formula (additive on `balanced` profile; default-on for `deep`, default-off for `fast`)
5. **M-2.2.5** Federation audit-aware feed (new optional column `audit_aware: true` on peer config; default OFF, opt-in during peer setup)

Each step independently revertable. Step 5 requires both ends upgraded; we ship with the opt-in flag default OFF for one full minor release before flipping.

### Tests

- Per-backend repo test: write 5 memories → walk chain → verify signature on each (PG / Oracle / Db2 / SQLite)
- Profile fan-out test: same query × 3 profiles → result-set superset relationship (fast ⊆ balanced ⊆ deep)
- Decay golden: 10 memories × 4 categories × 3 ages = 120 ordering assertions
- Federation cross-backend: PYTHIA (PG) → CERBERUS (Oracle DG standby per v6.1) → ACHILLES (Db2) → verify all three reconstruct the same Merkle root for a sealed window
- Adversarial: tamper with one entry's `payload_hash` after-the-fact → `mnemosctl audit verify` fails with `break-at-entry`

### Bench

- Write throughput: v6.1 baseline vs v6.2 audit-chain-on (target ≤8% p99 degradation)
- Search throughput per profile: 10 QPS × 5 min, report p50/p95/p99 + cache hit rate
- Cross-encoder rerank: CERBERUS bge-reranker-v2-m3 sustained 50 req/s with 100 pairs each (5K pairs/sec)

### Operational impact

- New service: `mnemos-reranker` on CERBERUS port 8090 (2GB VRAM, idle)
- New worker: `audit_sealer` co-resident with API (one per replica)
- New env vars: `MNEMOS_AUDIT_CHAIN=on|off`, `MNEMOS_AUDIT_ROOT_PRIVKEY=<b64>`, `MNEMOS_AUDIT_SEAL_WINDOW_SEC=60`
- New tables across 4 backends: `memory_audit_chain`, `memory_audit_roots`, `memory_category_decay`
- New routes: `/v1/audit/proof`, `/v1/audit/pubkey`, `/v1/federation/audit_roots`, `/v1/admin/category_decay/*`
- mnemosctl gains `audit verify <memory_id>`, `audit verify-window <root>`, `category-decay list|set|reseed` subcommands

### Effort estimate

| Component | Effort |
|---|---|
| Audit chain (table + sealer + 4 backends + tests) | 3 days |
| Constant-time auth compare | 30 min |
| Retrieval profiles (3 pipelines + reranker service + telemetry) | 3 days |
| Per-category decay (table + formula + admin + golden tests) | 1 day |
| Federation audit-aware feed | 2 days |
| Bench + blog narrative | 1 day |
| **Total v6.2 sprint** | **~2 weeks focused** |

## Explicitly NOT in v6.2

| Skipped | Why |
|---|---|
| WAL CRC32 + HMAC + AES-256-GCM (nexus pattern) | Oracle DG / Db2 HADR / PG-WAL already give the layer |
| OAuth 2.1 server (nexus pattern) | LAN-only fleet; static Bearer + per-scope keys + constant-time compare is enough |
| Sketch substrate (nexus pattern) | MNEMOS workload not sketch-shaped |
| Hot-reload source configs (nexus pattern) | Deferred to a v6.3 ops sprint; SIGHUP not load-bearing today |
| Per-write idempotency keys at `/memories` | Will land in v6.2 only if the audit chain doesn't naturally subsume it. Audit `entry_id` is UUIDv7 + caller-side; a second write of the same content from the same writer in the same second collides at `payload_hash` — that already gives idempotency cheaply. Decide after step M-2.2.1 lands. |

## Sequencing constraints

- v6.1 must ship first — audit chain references the v6.1 P3 #37 token-rotation work (the literal token used to POST audit entries would otherwise be the same value rotated)
- v6.1 F-1 (federation embedding copy) should land before step M-2.2.5; replicas need embeddings present to serve `deep` profile reranking
- CERBERUS reranker service requires the v6.1 NATS KV resilience work (item #15) if we want the reranker calls to share the same circuit breaker as Ollama calls; otherwise ship with a standalone breaker
