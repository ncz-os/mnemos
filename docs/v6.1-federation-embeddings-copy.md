# v6.1 F-1 — Copy embeddings via federation feed

**Backlog item:** v6.1-roadmap.md → "Federation feature backlog (added 2026-05-23) → F-1"
**Hive job:** `019e55de-f13a-7731-a10b-b661909db661` (mnemos:mnemos-v61-federation-embeddings)
**Status:** design draft 2026-05-23

---

## Problem statement

Federation pull (`/v1/federation/feed` → consumer) replicates memory rows but the
`embedding` `VECTOR(768)` column lands NULL on the replica. Replicas
(CERBERUS, ACHILLES) cannot serve vector search locally without recomputing
embeddings — pure duplicate work the primary already paid for.

Confirmed during 2026-05-23 CERBERUS standup: `fed:pythia:*` rows had no
embedding values. `semantic_search` against CERBERUS replica fell back to FTS
or returned empty result depending on caller path.

---

## Design

### Schema change (migration 0028)

Add per-peer opt-in flag to `federation_peers`:

| Column | Type | Default | Notes |
|---|---|---|---|
| `copy_embeddings` | bool / NUMBER(1) / SMALLINT | 0 | when 1, feed payload includes `embedding_b64`; off by default to preserve current bandwidth profile |

New migration files:
- `db/migrations/0028_federation_peers_copy_embeddings.sql` (PG)
- `db/migrations_oracle/0028_federation_peers_copy_embeddings.sql` (Oracle 23ai)
- `db/migrations_db2/0028_federation_peers_copy_embeddings.sql` (Db2)
- SQLite path: `ALTER TABLE federation_peers ADD COLUMN copy_embeddings INTEGER NOT NULL DEFAULT 0` (issued at startup if column missing)

### Wire format

`MemoryItem` in `/v1/federation/feed` response gains an OPTIONAL field:

```json
{
  "id": "mem_177...",
  "content": "...",
  "category": "feedback",
  ...,
  "embedding": "BASE64(float32×768 little-endian)",
  "embedding_model": "BAAI/bge-small-en-v1.5",
  "embedding_dim": 768
}
```

`embedding_model` lets the consumer detect model drift (replica with a
different embed model can choose to recompute, or accept the foreign vector
+ flag it as `embedding_origin=foreign`). Default behavior: accept verbatim
when models match; warn + skip otherwise.

`embedding_b64` only appears when the **caller's** peer config sets
`copy_embeddings=1`. Server-side filter so an unintended peer can never
trigger bulk embedding shipment.

### Server-side path (the federation primary)

`mnemos/api/routes/federation.py::federation_feed` reads
`request.state.peer_id` (already set by `require_federation_role` deps) and
loads `federation_peers.copy_embeddings` for that peer. Pass through to
`backend.federation.feed_query(... include_embedding=bool)`.

`mnemos/persistence/*/federation.py::feed_query` adds:
```python
async def feed_query(
    self,
    tx,
    *,
    since_id: str | None,
    limit: int,
    include_embedding: bool = False,
) -> list[dict]:
    cols = "id, content, category, ..., updated"
    if include_embedding:
        cols += ", embedding, '<embed-model-name>' AS embedding_model"
    ...
```

`_feed_item_from_row` (federation.py:160) serializes embedding bytes →
base64 when present.

### Consumer-side path (the federation replica)

`mnemos/federation/*_consumer.py` (or `nats_consumer.py`) decodes
`embedding_b64` if present and the consumer's local embed model matches
`embedding_model`. Insert path uses backend-neutral
`MemoryRepository.upsert(... embedding=bytes)` which already exists for the
write API.

Consumer config addition:
```
[federation.peers.pythia]
url = "http://192.168.207.67:5002"
copy_embeddings = true            # request embeddings from this peer
accept_foreign_model = false      # if peer's embed model != ours, skip the column
```

### Bandwidth assessment

For BAAI/bge-small-en-v1.5 (768 dims, float32):
- Per-memory embedding bytes: 768 × 4 = 3072 bytes (3 KB)
- 8235 memories on PYTHIA: ~25 MB initial sync; ~3 KB per ongoing delta
- Acceptable for LAN-local fleet (1+ Gbps). Not free for WAN federation —
  hence opt-in default OFF.

### Telemetry

`/v1/admin/federation_stats` gains per-peer columns:
- `embeddings_pulled_count` — total embedding rows received
- `embeddings_pulled_bytes` — cumulative bytes
- `embedding_model_mismatches` — count of skipped rows due to model drift

Updates to existing `federation_peers.total_pulled` counter unchanged.

## Acceptance criteria

1. **Default off, no behavior change:** `copy_embeddings = 0` for any peer →
   `/v1/federation/feed` payload identical to v6.0
2. **Opt-in on:** peer with `copy_embeddings = 1` receives embedding bytes in
   feed payload; replica inserts with embedding populated
3. **Model match enforcement:** if `embedding_model` differs from
   replica-local model AND `accept_foreign_model = false`, replica skips
   embedding column (memory row still lands; embedding stays NULL)
4. **Replica search works:** after a `copy_embeddings = 1` sync,
   `semantic_search` on the replica returns identical top-K vs primary for a
   prepared 100-query benchmark (Recall@10 ≥ 0.99)
5. **Bandwidth bound:** with `copy_embeddings = 1` enabled fleet-wide, total
   replication bytes is bounded by ≤ 6 KB per memory write (3 KB content +
   3 KB embedding); benchmarks confirm
6. **Telemetry:** `/v1/admin/federation_stats` reports per-peer embedding
   counters
7. **Cross-backend matrix:** test runs across PG → Oracle and PG → Db2 peer
   pairs; embedding bytes survive backend transition

## Sequencing within v6.1

This item is INDEPENDENT of the v6.1 P0 critical path (Oracle DG + Db2 HADR +
cross-backend federation HA). Can land mid-cycle as soon as schema migration
slot is free. Recommended order:

1. **F-1.1** migration 0028 (4 backends) — pure additive, no behavior change
2. **F-1.2** `feed_query(include_embedding=bool)` plumbing across 4 backends
3. **F-1.3** API surface change: response schema + server-side flag honor
4. **F-1.4** consumer-side decode + insert with model match
5. **F-1.5** admin telemetry + benchmark + docs

Each step independently revertable. F-1.4 specifically requires both ends
upgraded (sender + receiver); ship with `copy_embeddings = 0` for all
existing peers, flip per-peer after both sides confirmed on v6.1.

## Open questions

1. **Embedding model identifier scope:** do we ship just the HuggingFace
   repo path (`BAAI/bge-small-en-v1.5`) or also the revision SHA? Revision
   SHA gives stricter compat but is brittle when the model file is
   regenerated locally. Recommend: ship `model_name + dim` only;
   revision-pinning is over-engineering at this stage.

2. **Backwards-compat for old peers:** a v6.0 peer pulling from a v6.1 peer
   with `copy_embeddings = 1` will receive an unknown `embedding` field on
   `MemoryItem`. Pydantic forbids extra by default. Recommendation: set the
   model config to `extra = "ignore"` on `MemoryItem` so v6.0 silently
   ignores. Already the safest default for cross-version federation
   compatibility.

3. **Cache invalidation on peer config change:** flipping
   `copy_embeddings = 0 → 1` does not automatically re-pull historic rows.
   Recommend: add `mnemosctl federation backfill-embeddings <peer>` that
   walks `last_pulled_id` backward, issuing scoped re-pull requests with an
   embedding-only delta endpoint (out of scope for F-1; followup F-1.6).

4. **Audit-chain interaction (v6.2 nexus pattern):** embedding bytes are NOT
   included in `payload_hash`. The v6.2 design (docs/v6.2-nexus-pattern-
   adoption.md) hashes a SHA-256 of the embedding bytes instead, so
   re-shipping an embedding for F-1 does NOT change the audit hash. This
   keeps F-1 and v6.2 cleanly orthogonal.
