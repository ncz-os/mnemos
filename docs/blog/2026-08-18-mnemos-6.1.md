# MNEMOS 6.1: the release where the checks got checked

MNEMOS 6.1 is out. On paper it is a patch line on top of 6.0 — no new
subsystems, no new API surface worth a migration guide. In practice it is the
most useful release we have shipped, because almost every fix in it belongs to
one family:

**A guard existed. It was correct. It never ran on the path that failed.**

That pattern showed up in the rate limiter, in federation, in schema
migrations, and in the container image itself. Each one passed its tests. Each
one was broken in production. Here is what we found and what we changed.

## Rate limiting no longer takes the API down with it

The `server` profile defaults its rate-limit store to Redis. The published
single-container image ships no Redis. So the limiter raised `ConnectionError`
on every request, and SlowAPI handed that to its *rate-limit-exceeded* handler,
which reads `exc.detail` — an attribute only `RateLimitExceeded` has. The
handler itself then raised:

```
AttributeError: 'ConnectionError' object has no attribute 'detail'
```

Result: **HTTP 500 on every route, `/health` included**, from a container that
logged "Application startup complete" and looked perfectly healthy.

We shipped a fail-open handler for this in 6.1.0. It did not work, and the
reason is the interesting part. `SlowAPIMiddleware` resolves handlers by
*exact exception type*:

```python
exception_handler = app.exception_handlers.get(type(e), _rate_limit_exceeded_handler)
```

We registered our handler for `RateLimitExceeded`. A store outage raises
`ConnectionError`, which matches nothing, so slowapi fell back to its own
handler and died exactly as before. Registering for `Exception` would not have
helped either — the lookup is not subclass-aware, and the set of errors an
arbitrary storage backend can raise is not enumerable.

Worse, our *test* passed the whole time, because it called the handler
directly and never went through the middleware.

6.1.7 fixes it at the limiter instead: `RateLimitExceeded` is re-raised,
everything else is swallowed loudly, so slowapi never sees a foreign exception.
That covers the decorator path too. Swallowing alone was not enough — the
middleware then injects headers from state the aborted check never set, which
merely traded one `AttributeError` for another.

**Losing rate limiting must degrade to "unlimited", never to "the API is
broken."** A protective measure that cannot function must not take the service
with it.

## Federation had not replicated in three months

Three independent defects, two of which failed silently.

**Compatibility was decided on `major.minor`.** A 6.0 node refused a 6.1 peer
outright, so *every* minor release broke federation until an operator hand-set
`compat_mode=permissive` on each peer. Minor releases are backwards compatible
by our own versioning contract; the decision belongs on the major version.

**The feed offered nothing.** `create_memory` writes `permission_mode` 600, and
the world-read gate wants `% 10 >= 4`. So peers pulled successfully, reported
`{"pulled": 0}`, and logged no error. That is the worst kind of bug: a green
check mark over a system doing nothing. Nothing had replicated since May.

**LAN peers could not be registered.** The private-address and insecure-scheme
flags both defaulted false, so a private fleet could not register its own
peers.

While fixing the last one we split the SSRF guard rather than loosening it.
Link-local (cloud instance metadata), multicast, reserved and unspecified
addresses are refused on every network regardless of configuration; RFC1918 and
loopback are what the flag gates. A hostname that resolves to 169.254.169.254
is still refused with the flag on. The repository's own test caught an earlier
version of this change that would have opened exactly that hole.

## Vectors are backend-specific artifacts

The subtlest thing we learned this cycle has no CVE and no stack trace.

Two nodes both reporting `embedding_model=bge-m3`, `embedding_dim=1024` are not
necessarily in the same vector space. We measured a **0.778 cosine** gap
between two nodes running the same model at the same width — the difference was
*pooling*. One server had been started with mean pooling on a model that uses
CLS. Mean-pooled vectors of a CLS model are not that model's embeddings at all,
but they are internally self-consistent, so retrieval "works" and nothing ever
errors.

For scale: switching quantisation on the same model moved vectors by **0.0064**
(cosine 0.9936). The thing everyone worries about was 30× smaller than the
thing nobody was looking at.

So 6.1 makes federation's embedding adoption **fail closed**. A peer vector is
adopted only when both sides' fingerprints are known *and* agree. Previously
each comparison was guarded on the local value being truthy, which meant a node
that could not resolve its own embedder skipped every check and accepted
anything. The content still lands either way; only the vector is declined, and
a local re-embed fills it in the node's own space.

A model *name* is not a fingerprint. Engine, quantisation, pooling,
normalisation, sequence length, tokenizer and chunker all move the vector.

## Backends that are not PostgreSQL

MNEMOS supports PostgreSQL, SQLite, Oracle, Db2 and MySQL/MariaDB. CI has the
first two. Every defect below was invisible until a real host ran it:

- **Oracle could not claim deletion work.** `ORA-02014` on every tick, both
  workers stuck in error. The code already knew Oracle rejects `FETCH FIRST`
  with `FOR UPDATE` and used a `ROWNUM` view instead — which has the same
  defect, because the lock still targets a view.
- **Oracle could start exactly once.** A migration relaxes a column, and
  migrations replay on every boot. Oracle rejects a nullability change that is
  already satisfied, so the second start aborted. The guard for this existed on
  the main branch and was missing from the release branch.
- **Db2 could not migrate.** Nine consecutive `ALTER`s put the table into
  reorg-pending, then `CREATE INDEX` was refused. We now reorganise and retry on
  that specific error rather than adding an unconditional `REORG` that would
  rewrite the table on every boot.
- **Db2 depended on Oracle compatibility mode.** It inherited `ROWNUM`, which on
  Db2 exists only under `DB2_COMPATIBILITY_VECTOR=ORA`. Our instance had it set,
  which is why it appeared to work; a stock Db2 would have failed.
- **MariaDB could not create two tables.** A foreign key and its referent must
  share charset *and* collation; the backend declared ascii ids while inheriting
  utf8mb4 table definitions. `errno 150`.
- **MariaDB could not create a federation peer at all.** `CAST(x AS JSON)` is
  not implemented there. Peer creation was the only way to tell a node about a
  peer, so the failure was total.

None of these are exotic. They are what happens when a portability layer is
only ever exercised against one database.

## The image required an instruction set your CPU may not have

`llama-cpp-python` compiles from source, and ggml defaults to
`-march=native` — against the *build* machine. Our CI runner has AVX512. Much
of the world does not.

The failure mode is the nastiest in this whole release. `import llama_cpp`
**succeeds**, so the container starts and `/health` returns 200. The illegal
instruction fires on the first *call* into the library — that is, on the first
write. The process dies, the supervisor restarts it, health goes green, and the
client sees an empty response with nothing in the log.

Fifty-three restarts before anyone worked out what was happening.

The image now pins an explicit portable baseline instead of inheriting whatever
hardware CI happened to run on. That property was invisible in the Dockerfile
before; it is now stated.

## Performance and hygiene

- Bulk create batches its embeddings and commits once.
- Webhook delivery batches inserts and publishes after commit.
- NATS: circuit-breaker failures reset on success, concurrency leases renew
  while a call is in flight, and the visibility epoch moved to JetStream KV.
- The GRAEAE consultation audit chain **never verified** — writers, verifier and
  fetch disagreed about what was being hashed, so the verifier hashed `None` for
  half its inputs and rejected every row ever written. Now one shared, signed,
  versioned implementation.
- Migrations are replayable: three statements raised "already exists" against a
  real database, and because a failed statement aborts the surrounding
  transaction, everything after them was silently skipped.
- Architecture is enforced, not aspirational: import-linter contracts pass, so
  the persistence layer can no longer reach up into workers or domain.
- Container images build on native runners per architecture instead of under
  emulation. The whole matrix now takes about five minutes.

## What we would tell you to take from this

Most of these bugs were not "we forgot to handle X." They were "we handled X,
we wrote a test for X, and the handler was never reached."

If you want to catch this class in your own systems, the check that works is
uncomfortable and cheap: **make the test fail against the unfixed code.** Not
"assert the function behaves correctly" — assert that the *system* fails
before the change and passes after. Every fix in 6.1.7 carries a test that was
run against the broken version and failed there.

The second habit is to doubt the instrument before the product. Twice this
cycle a measurement said something impossible, and the measurement was wrong —
a performance collector that had been reporting a stale idle container as the
production API for weeks, and a process uptime that could not possibly be older
than the restart it was supposed to describe.

MNEMOS 6.1 is Apache 2.0. Upgrade notes and the full changelog are in the
repository.
